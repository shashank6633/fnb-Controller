# Valet Parking module — the owner's specification (verbatim)

Received 2026-11-09. Saved unchanged; build decisions live in `VALET-BUILD-STATE.md`
and `docs/valet/DESIGN.md`, never here.

---

You are the senior engineer working inside my existing FNB Controller application. Implement a complete Valet Parking module, centred on a dedicated Valet Head Dashboard, with an attendant interface and a guest web pass. Build working functionality, persistent data, server-side permissions, background processing, and tests. Do not stop at a plan or a frontend mockup.
Use only FNB Controller and the venue’s own branding. Create original UI and copy that match the existing application. Do not introduce third-party valet product names, logos, links, or copied assets anywhere in the implementation, sample data, comments, or documentation.
1. Inspect the existing application before changing it
Read repository instructions and inspect the framework, routing, database, authentication, roles, tenant/outlet model, UI components, notifications, media storage, background jobs, reporting, and tests. Identify existing table, reservation, customer, bill, and staff entities that this module can reuse. Present a concise implementation plan, then proceed.
Extend the current architecture and design system. Reuse existing infrastructure and avoid replacing the app or adding a second authentication system. Preserve unrelated changes. Make reasonable implementation decisions and document assumptions; ask only when a missing decision blocks safe implementation. If this is not the FNB Controller repository, ask for the correct repository rather than inventing an app.
Enable the module per outlet with feature flags. Develop and test locally; do not deploy to production, purchase hardware, activate paid services, or send real customer messages as part of development.
2. Roles and access
Map these capabilities into existing roles, adding roles only where necessary:
* Owner/Admin: Enable valet per outlet, manage configuration, retention, staff permissions, integrations, and authorised multi-outlet reports.
* Valet Head: Operate the live board for assigned outlets; manage shifts, dispatch, reassignments, parking zones, key custody, incidents, escalations, and operational reports. Priority changes and exceptional handovers require recorded reasons.
* Valet Attendant: Check vehicles in, capture condition, record parking and key locations, claim the next eligible task, update their assigned work, and perform verified handovers. No unrestricted access to customer history, revenue, or other outlets.
* Host/Cashier/Floor Manager: Link an authorised dining visit and request pickup on a guest’s behalf after confirmation. Do not expose unrelated valet administration.
* Guest: See and operate only their own active pass, without installing an app or creating an account.
Enforce authorisation on every API, subscription, report export, file access, and background operation. Hiding buttons is not an access control.
3. Arrival, check-in, and parking
Support both staff-assisted check-in and a guest scanning a venue QR or tapping a venue NFC card. A shared venue card opens the check-in entry point; it must never contain a guest’s private pass or expose another vehicle.
For guest-led check-in, create a short-lived pending session and pairing code. An authenticated attendant confirms the guest, vehicle, and physical key tag before activating the pass. Expire abandoned sessions. Restore an existing pass only for an authenticated guest session or a verified recovery flow.
Record outlet, arrival time, plate, vehicle make/model/colour where available, reusable key tag or paper ticket, attendant, and optional guest name/mobile. Mobile must be optional when the guest uses the browser or a paper claim receipt. Support configurable required fields and prevent duplicate active tag assignments. Warn about duplicate active plates and require staff resolution.
Allow up to six condition photos, annotations for existing damage, and notes. Show upload progress and allow retry. Record who captured them and when. Make photo policy configurable so a busy arrival can be completed with an explicitly recorded exception.
Record parking zone, spot/landmark, key rack/hook, and key custodian. Support quick zone buttons and free-text notes. Keep unparked arrivals visible until parking is confirmed. Track vehicle location and key location separately. Log every custody transfer and physical movement.
Issue an outlet-branded guest pass with vehicle summary, masked plate, visible tag, status, help action, and pickup controls. An unguessable session credential must be separate from the visible tag. For guests without usable phones, issue a printed or staff-assisted claim credential and support verification at the desk.
4. Guest pickup and scheduled retrieval
Offer Request now, In 5 minutes, In 10 minutes, and a configurable later time within service hours and capacity. Show request receipt, current status, estimated queue position when meaningful, an estimated readiness range, pickup gate, and an I’m outside action. Queue position must not reveal other guests’ details.
Treat requested pickup time as a target, not a guarantee. Estimate readiness from the eligible queue, available attendants, recent retrieval durations, and parking zones. Use a configurable estimate when data is insufficient; never show fabricated precision. Let the Valet Head adjust an ETA with a recorded reason.
Allow cancellation or rescheduling before work is claimed. Once retrieval is assigned or underway, route changes to staff for acknowledgement instead of silently cancelling physical work. Repeated taps and retries must return the same active request. Multiple vehicles linked to one guest must require explicit vehicle selection.
5. Queue, dispatch, and physical state
Implement an explicit server-side transition model. Prefer separate vehicle and pickup states rather than one ambiguous status:
* Vehicle: `CHECKED_IN → PARKING → PARKED → RETRIEVING → READY_AT_GATE → HANDED_OVER`.
* No-show branch: `READY_AT_GATE → RELOCATING → HOLDING_NEAR_GATE → RETRIEVING → READY_AT_GATE`, with staff confirmation of each physical move.
* Pickup: `SCHEDULED → QUEUED → ASSIGNED → IN_PROGRESS → READY → COMPLETED`; cancellation and no-show outcomes preserve history and allow a new pickup attempt.
Adapt names to the repository, but document allowed transitions, actors, guards, and timestamps. A cancellation must not close a vehicle session while the venue still holds the car. A timer or RFID observation must not falsely mark a physical move complete.
Use a durable scheduler to release future requests when retrieval should begin. Define the eligibility rule explicitly using target time and estimated retrieval lead time. Use FIFO among eligible requests, with stable ordering and a documented policy for overdue work. Do not let a far-future booking block a request that is ready to dispatch. Head-approved exceptions require an audit reason.
Provide Take next car. Claim the task atomically so concurrent attendants cannot receive the same car. Respect shift availability and default to one active physical task per attendant. Authorised manual assignment must use the same concurrency safeguards.
Reassignment must preserve custody and notify both attendants. A lost connection must not automatically dispatch a second attendant for a car already being moved. Require an acknowledged staff handoff or Valet Head resolution for uncertain work.
6. Dedicated Valet Head Dashboard
Build an operational screen within FNB Controller, usable on desktop, tablet, and phone. Include outlet selection within permissions, service date/shift, search, filters, connection status, and a last-updated indicator.
Show live counts for arrivals, parked vehicles, scheduled pickups, unclaimed requests, retrievals, cars at the gate, overdue tasks, available attendants, and occupied parking/gate/holding spaces. Show request-to-ready average and p90, with clear definitions.
Provide board/list views for Pending check-in, Parking, Parked, Scheduled, Requested, Assigned/Fetching, Ready at gate, Holding, and Completed. Include a prominent exceptions panel for overdue requests, missing locations/keys, failed notifications, incidents, and unavailable staff.
Each operational card should expose the tag, permitted plate detail, vehicle description, parking/key location, relevant timestamps and timers, guest-outside flag, assigned attendant, parked-by/fetched-by names, ETA, and next permitted action. Mask contact information unless needed for an authorised task.
Support assignment/reassignment, priority with reason, ETA adjustment, incident recording, controlled contact actions, parking relocation, exception resolution, and audited voiding of test/duplicate records. Do not hard-delete operational history from the board.
Add a team panel showing on-shift, available, busy, on-break, and off-shift staff, active tasks, hours, and completed jobs. Support shift start/end and handover reconciliation of remaining cars, keys, and unresolved incidents. Ending a shift with outstanding custody requires an acknowledged transfer.
7. Attendant interface and gate operations
Create a mobile-first interface with large tap targets, clear labels, high contrast, and fast camera/QR/manual input. Prioritise Start shift, New check-in, Scan tag, Take next car, My task, Set parking spot, Mark ready, Verify handover, and Report problem.
When a car reaches the gate, start a configurable 2/3/5/10-minute dwell timer; default to 3 minutes. Notify the guest and show the countdown. On expiry, highlight the problem and prompt staff to move the vehicle to a near-gate holding area if space exists. Staff must record the new location. Support Guest went back inside and Guest has returned without losing the original history.
Track gate and holding-area capacity. When full, warn the head and adjust dispatch/readiness expectations. Provide a safe staff-controlled exception instead of creating an unrecoverable blocked queue.
For handover, require an authenticated staff member to match the vehicle and key tag and validate a short-lived, single-use guest credential, such as a rotating QR or rate-limited code. Consume it atomically with closing the session. Visible tag numbers and number plates are identifiers, not secrets.
A lost phone, failed verification, or disputed claim goes to a Valet Head recovery flow with a documented reason and verification method. Do not collect government-ID images by default. Prevent reuse of old passes after completion or tag reassignment.
8. Notifications and closing-time management
Provide live in-app updates independently of external messaging. Use the existing real-time mechanism, with reconnect/resync and a polling fallback where appropriate.
Integrate WhatsApp through the existing approved provider or an official API adapter. Support linking a verified messaging identity to a pass, check-in, ETA, ready-at-gate, and holding messages, and pickup replies or buttons. Resolve outlet and vehicle explicitly if more than one session matches. A phone number typed into a form is not a verified messaging identity.
Record channel consent and opt-out; respect current provider rules for approved templates and messaging windows. Validate webhook signatures, reject replay, deduplicate provider events, and track queued/sent/delivered/failed separately. Never report delivery simply because a send request was accepted.
Use a durable outbox/job system for retries, scheduling, and escalation. Implement notification deduplication, bounded retry/backoff, and an actionable failed-delivery view. Stop obsolete messages after cancellation or completion. If credentials/templates are missing, provide a clearly labelled local simulator and precise setup instructions; never fake a live integration.
Offer browser sound/vibration after permission and a user gesture where supported, plus configurable reminders. Do not promise continuous ringing on locked phones or guaranteed background delivery. Track alert acknowledgement separately from task acceptance.
Escalate unclaimed requests after a configurable threshold, default 5 minutes; also escalate prolonged fetching, an outside guest waiting, gate dwell overruns, and no staff on shift. Deduplicate and stop resolved escalations.
Add an optional closing-rush mode that sends consented pickup-planning prompts in capacity-aware batches 30–45 minutes before close. Only a guest’s confirmed choice should create or modify a pickup. Support venue business dates that cross midnight.
9. Paper-ticket compatibility and FNB integration
Support bill-folder or table QR entry for venues retaining paper tickets. Guests can enter a paper ticket and vehicle details. Validate against an issued ticket/session and prevent duplicate active use. Where curbside registration was skipped, accept only a pending verification request; staff must confirm the issued physical stub before dispatch. A valid ticket-book number alone must not establish ownership or authorise retrieval.
Allow an optional relation to an existing customer, reservation, dining visit, table, and bill. Model multiple vehicles per dining visit and keep links valid through table transfers or bill splits. Table links must resolve the current authorised visit, not a previous guest.
Add appropriate valet status and guest-confirmed Request pickup actions to existing host/cashier screens. Bill printing, settlement, or table closure can offer a pickup prompt but must not automatically fetch or release a vehicle. Valet must remain usable without a dining link and after a dining bill closes.
If fee or payment infrastructure already exists, design an optional extension point for valet charges/validation. Keep new payment flows, tips, and payment-based handover restrictions outside the initial required scope.
10. QR, NFC, and RFID implementation
QR plus manual fallback is mandatory and must deliver the complete core flow without new hardware.
For NFC, support compatible NDEF tags containing an HTTPS entry URL for guest check-in, bill-folder access, or staff tag lookup. Differentiate an operating-system URL tap from JavaScript Web NFC reading. A guest URL tap should not depend on Web NFC. Use browser capability detection and verify current device support before implementing optional in-browser scanning/provisioning. Do not assume iPhone Safari can use Web NFC; preserve QR/manual alternatives.
Provide tag inventory, assign/unassign, disable/replace, duplicate checks, and provisioning instructions. NFC/key tags contain only an opaque reference or public entry URL, never personal data or a private guest credential. Require staff authentication for operational lookup/actions. Tag IDs and ordinary static NFC contents are not proof of identity and may be copied.
Treat long-range UHF RFID as an optional later hardware integration. Do not assume normal phone NFC reads UHF tags. Define a reader adapter, device registration, outlet binding, reader-health status, authenticated event ingestion, and a simulator. Normalise events with event ID, reader ID, tag ID, zone/antenna, observed time, and received time. Deduplicate repeated reads and reject unauthorised devices or stale/replayed events.
RFID may assist key inventory or suggest vehicle-zone observations after physical validation. It must never autonomously authorise handover, identify an owner, or claim exact location from a single uncertain read. Gate/barrier actuation is outside scope. Keep real RFID disabled until reader model, SDK/protocol, placement, and field tests are confirmed.
11. Data, security, and reliability
Reuse existing entities where possible; introduce appropriate records for vehicle sessions, guest credentials, pickup attempts, assignments, reusable tags, ticket books/issuance, locations, key custody, shifts, condition media, incidents, notification attempts, consent, device events, and audit history.
Every record and query must respect tenant/outlet scope. Add suitable constraints/indexes for active tag uniqueness, one active pickup per vehicle, atomic task claims, credential consumption, and search. Use transactions, idempotency keys, and version/conflict checks for concurrent writes. Treat the server as authoritative.
Store credential hashes where suitable, expire/revoke credentials, protect cookie-based actions from CSRF, and rate-limit pairing, lookup, recovery, and verification attempts. Avoid enumeration and redact pass tokens/contact details from logs. Keep guest passes out of search engines and shared caches. Use private media storage, validated uploads, short-lived authorised access, and safe CSV exports.
Show disconnected/stale data clearly. Allow bounded temporary local drafts for check-in details where appropriate, with device-local protection, expiry, and cleanup on logout. Do not report an offline request, assignment, or handover as confirmed. Queue only operations safe to replay, reconcile conflicts explicitly, and document a staff-managed paper fallback for full outages.
Offer configurable retention for valet-only personal details and photos, with a proposed maximum normal retention of 12 months unless a different approved policy applies. Implement cleanup/anonymisation, narrowly scoped incident holds, and documented backup expiry. Do not delete shared FNB customer or financial records. Keep operational audits append-only during retention, then redact personal data as required. Do not describe this configuration as automatic legal compliance.
Returning-guest convenience must require consent and remain within the authorised business scope. Do not create automatic identity sharing across unrelated outlets or businesses.
12. Reports, design, and settings
Report arrivals, completed handovers, peak hour, occupancy, task claim time, retrieval time, request-to-ready wait, scheduled-target lateness, gate dwell, no-shows, incidents, and jobs/hours per attendant. Show average, p90, and maximum where useful. Define denominators and exclude void/test records. Separate immediate-request waiting time from intentional scheduled delay. Permit authorised date/outlet/shift filtering and CSV export.
Settings should cover operating hours, business-day boundary, capacity, zones, pickup options, dwell limits, escalation thresholds, notification consent/templates, required photos, language, and optional hardware.
Use the application’s components, colours, spacing, typography, and navigation. Make status understandable through text/icons as well as colour. Include accessible controls, loading/empty/error/stale states, mobile camera fallback, English and Hindi strings through the existing localisation system, and venue logo/name on the guest pass. Avoid an unrelated standalone dashboard design.
13. Verification and delivery
Use the existing test framework. Add meaningful tests for state transitions, queue eligibility/fairness, simultaneous claims, request retries, scheduling across midnight, assignment handoffs, gate no-shows, credential replay, tag reuse, paper-ticket verification, and cross-outlet access. Cover notification failures/duplicate webhooks, missing hardware, retention scope, and offline conflict handling.
Run complete browser-to-server-to-database scenarios for guest check-in through handover, a scheduled pickup, a phone-less guest, a no-show returned to holding, and Valet Head intervention. Verify updates on two simultaneous staff clients. Test representative closing-rush data and state the tested load and observed limitations; do not invent performance results.
Deliver in working increments: core QR operations and dashboards first; then scheduling, photos, reports, paper mode, FNB links, and notification adapters; then NFC provisioning and optional RFID adapter/simulator. This sequencing does not remove required software features from scope. Real external integrations may remain explicitly unconfigured if credentials or hardware are unavailable.
Provide migrations, sample data using fictional guests, environment-variable examples without secrets, setup instructions, notification-template requirements, hardware compatibility notes, a shift-operation guide, and deployment/rollback notes for later review. Finish with what works, checks actually run, configuration still required, and any remaining limitations. Never claim a mock provider, simulated reader, or untested physical device is production-verified.
Begin by inspecting the repository, then implement the module end to end.
